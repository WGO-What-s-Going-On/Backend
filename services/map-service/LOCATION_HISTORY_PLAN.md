# 사용자 위치 갱신 이력

## 이번 단계

Map은 유효한 `PUT /api/v1/location` 요청마다 Cassandra `user_location_history`에 한 행을 기록한다. 같은 좌표나 재시도도 각각 새 기록이다. 서버가 생성한 `timeuuid`가 갱신 ID와 정렬 키이며, UTC 일별 버킷 안에서 내림차순으로 저장한다. 쓰기 전에 이전 위치를 조회하거나 이동 거리·간격을 판정하지 않는다. Cassandra 쓰기가 실패하면 `503`이다. 성공한 이력의 최신 위치는 Redis에 300초 캐시하며, 동시 요청이 역순으로 완료되어도 이전 위치가 최신 캐시를 덮지 않도록 정렬 키를 비교한다. Redis 캐시 쓰기가 실패해도 Cassandra 이력 기록은 성공으로 처리한다. 이때 기존 캐시가 남아 있으면 TTL 만료 전까지 판정에 이전 위치가 쓰일 수 있다.

생성·참여 판정은 Redis 최신 위치 캐시를 먼저 읽는다. 캐시가 없거나 Redis를 사용할 수 없으면 Cassandra의 오늘 버킷 최신 행을 읽고, 비어 있으면 전날 버킷을 읽는다. 기존 5분 신선도, 5초 초과 미래 시각, 거리 판정과 HTTP/gRPC 메시지 형식은 유지한다. 원본 좌표 이력은 7일 TTL로 조회 가능하며 6시간 TimeWindowCompactionStrategy를 사용한다. TTL 만료는 조회 제외 시점이고 물리 공간은 이후 compaction에서 회수한다.

Gateway는 기존 전역 IP별 100건/분 제한과 별도로 `PUT /api/v1/location`에 IP별 최근 60초 60건 제한을 둔다. 61번째 요청은 Map에 전달하지 않고 `429`와 `Retry-After`를 반환한다. Redis 제한 저장소를 사용할 수 없으면 위치 갱신을 차단한다. 공유 IP의 여러 사용자가 제한을 함께 사용한다.

## 배포 및 후속 단계

새 테이블을 먼저 배포한 다음 모든 Map 쓰기 인스턴스를 이력 쓰기로, 판정 인스턴스를 이력 읽기로 전환한다. 기존 `user_locations` 행은 과거 요청 이력으로 이관하지 않는다. 운영 위치 갱신은 인증 연동 전까지 계속 `503`이므로 첫 새 요청 전에는 위치가 없을 수 있다. 전환을 확인한 후 기존 최신 위치 테이블을 폐기한다. 갱신 ID가 없는 기존 캐시 값은 읽기에서 무시하고 새 형식으로 교체한다.

후속 단계에서는 Gateway 사용자 인증과 사용자별 토큰 버킷(5초당 평균 1건, 최대 2건 순간 허용량)을 도입한다. 조사 API에는 권한, 기간·사용자 범위 제한, 접근 기록, 삭제 처리가 필요하다. Post Service 판정 결과에는 사용한 갱신 ID와 시각을 연결해야 한다. 신고 사건 증거의 별도 보존 기간도 정해야 한다. 이 이력은 서버가 수락한 좌표 요청의 기록이며 실제 이동이나 GPS 조작을 입증하지 않는다.
