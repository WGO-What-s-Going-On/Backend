# 사용자 위치 갱신 이력 계획

## 목적과 현재 상태

Map Service는 앞으로 사용자별 **위치 변경 로그(위치 갱신 요청 이력)**를 Cassandra에 남긴다. 이 이력의 목적은 게시물 생성·참여 시 최근 위치를 판정하고, 위치 조작 의심이나 부정 이용 신고를 조사할 때 당시 제출된 위치와 시각을 확인하는 것이다. 이력만으로 실제 이동이나 GPS 조작이 증명되지는 않는다. 서버가 수락한 위치 갱신 요청을 기록하므로 좌표가 같아도 새 요청이면 새 기록이며, 연속적인 실제 이동 경로를 보장하지 않는다.

현재 구현은 이 계획과 다르다. `PUT /api/v1/location`은 Cassandra `user_locations`의 `user_id` 한 행을 갱신하고 Redis에 300초 캐시한다. 이전 요청의 좌표는 조회 가능한 이력으로 남지 않는다. gRPC 생성·참여 판정은 이 최신 행을 읽고 5분 유효성을 확인한다. 운영 위치 갱신은 Gateway 사용자 인증 연동 전까지 503으로 차단된다.

## 목표 동작

1. 인증된 사용자의 유효한 `PUT /api/v1/location`마다 Map이 서버 수신 시각과 고유한 갱신 ID를 부여하고 Cassandra 이력 행을 쓴다. 클라이언트가 보낸 사용자 ID나 시각을 이력의 기준으로 신뢰하지 않는다. 재시도 때문에 같은 요청이 중복 기록되지 않도록 요청 식별 방법을 정한다.
2. 위치 판정은 Cassandra 이력의 가장 최근 항목을 기준으로 한다. 현재의 5분 경과·5초 초과 미래 시각 거부와 정확한 거리 계산은 유지한다. Redis가 최신 항목을 캐시할 수 있지만 Cassandra 이력이 원본이며 캐시 장애 시 이력을 조회한다.
3. 조사 시에는 권한 있는 내부 흐름에서 기간과 사용자 범위를 제한해 이력을 읽는다. 생성·참여 판정에 사용한 **갱신 ID와 시각**을 해당 행위의 근거와 연결해야 어떤 위치가 판정에 쓰였는지 특정할 수 있다. Moderation Service가 Map의 Cassandra를 직접 읽지 않도록 Map 소유의 내부 조회 계약을 둔다.
4. 원본 좌표를 일반 애플리케이션 로그, Redis Stream 이벤트, 분석 지표에 복사하지 않는다. 이력 조회의 권한·사유·접근 기록과 사용자 삭제 요청 처리를 함께 설계한다.

## 구현 계획

1. **수집 범위와 보존 기준 결정.** 요청마다 기록할지, 전송 간격·이동 거리 기준으로 요청 자체를 제한할지 정한다. 위치 정확도 등 조사에 필요한 입력 항목, 원본 좌표의 보존 기간, 신고 사건에 필요한 근거의 별도 보존 기간, 삭제·동의 철회 절차를 제품·개인정보 정책과 맞춘다. 이력 보존 기간은 적어도 현재의 5분 판정창보다 길어야 한다. 구체적인 값들은 아직 확정되지 않았다.
2. **이력 테이블 설계.** Map 소유의 Cassandra 테이블을 사용자 ID와 UTC 시간 버킷으로 분할하고, 서버 기록 시각의 내림차순 클러스터링 키와 갱신 ID를 둔다. 각 사용자·버킷의 최신 1건을 읽는 조회와 제한된 기간의 조사 조회를 지원한다. 버킷 크기는 사용자당 최대 갱신 빈도와 파티션 크기 측정 후 정한다. 보존 기간이 결정되면 이력 TTL과 시계열 compaction을 설정한다. TTL 만료 후 물리 공간 회수는 compaction에 의존하므로 삭제 요구의 완료 기준도 별도로 정의한다.
3. **쓰기·읽기 경로 전환.** `PUT`은 이력 쓰기가 성공해야 200을 반환한다. Redis는 최신 이력의 파생 캐시로 유지한다. 동시·역순 도착 때문에 오래된 갱신이 캐시의 최신 값을 덮지 않도록 시각/갱신 ID를 비교한다. gRPC 판정과 캐시 미스 조회는 오늘 버킷의 최신 행을 읽고, 자정 경계에서 필요하면 이전 버킷도 확인한다. 5분을 넘은 기록은 이력에 남아 있어도 판정에는 사용하지 않는다.
4. **기존 데이터와 배포 전환.** 기존 `user_locations` 행을 실제 과거 갱신 로그로 둔갑시켜 이관하지 않는다. 순차 배포 중 구·신 인스턴스가 함께 동작하는 기간을 고려해 쓰기·읽기 전환 순서를 정하고, 모든 쓰기 인스턴스가 이력을 남긴 뒤 판정 원본을 이력으로 바꾼다. 전환 기간에는 기록 누락·중복과 캐시 역전 여부를 측정한다.
5. **행위 근거와 조사 조회.** MapAuthorization 응답 또는 별도 내부 계약에 판정에 사용한 갱신 ID·시각을 추가하고, 허용·거부 결과 및 사유를 게시물 생성·참여 시도와 연결한다. 계약 변경 전 생산자·소비자와 하위 호환성을 확인한다. 조사 조회는 Map이 인증·인가·기간 제한·접근 기록을 적용해 제공한다. 신고 사건의 증거 보존이 일반 이력 TTL보다 길어야 한다면 Moderation Service 소유의 사건 근거로 명시적으로 분리한다.
6. **검증과 운영.** 반복 요청, 중복 재시도, 동시 갱신, 날짜 경계, Redis 장애, Cassandra 쓰기 실패, TTL 만료, 삭제 요청, 권한 없는 조사 조회를 테스트한다. 사용자당 쓰기 빈도, 파티션 크기, 조회 지연, TTL/tombstone·compaction 지표를 관측한다. 원본 좌표는 로그와 지표에 남기지 않는다.

## 결정이 필요한 항목

- 갱신 요청 전송 기준과 예상 최대 빈도: 모든 GPS 변화인지, 최소 시간·거리 기준을 둘지
- 원본 위치 이력 및 신고 사건 근거의 보존 기간과 삭제 처리 기준
- 조사에 필요한 위치 정확도·부가 정보, 조사 권한을 가진 역할
- 요청 재시도 식별자와 생성·참여 판정 근거를 연결할 계약
